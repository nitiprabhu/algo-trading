1. Vision & Product Goals
ChartEdge AI is an AI-powered technical analysis SaaS platform designed exclusively for NSE India, targeting Nifty 50 and Nifty Bank instruments. The system ingests real-time and historical OHLCV data from the INDstocks API, computes a multi-indicator technical confluence stack, and passes enriched chart snapshots to an AI reasoning engine (Claude) which generates BUY/SELL/HOLD signals with confidence scores, risk parameters, and trade rationale. The platform starts as a paper trading simulator and is architected to plug into live order execution (INDMoney API) as a Phase 2 upgrade.

1.1 Core Objectives
Maximum accuracy of intraday signal generation using pure technical chart analysis
AI-assisted confluence — no single-indicator decisions; always require multi-indicator agreement
Full paper trading loop with P&L tracking, trade log, and accuracy reporting for minimum 1 month
Modular, expandable architecture: new indicators, new instruments, and live execution can be added without re-architecting
Near real-time operation: signal latency under 5 seconds from candle close to signal output

3. Functional Requirements
3.1 Module 1 — Market Data Ingestion
3.1.1 Historical Data Loader
On startup, pre-fetch last 90 days of OHLCV data for both instruments across all required timeframes (1m, 5m, 15m, 1hr, 1D)
Store in local time-series DB (TimescaleDB or InfluxDB)
Support backfill — detect gaps and re-fetch missing candles automatically
Normalize timestamps to IST and forward-fill exchange holidays

3.1.2 Real-Time WebSocket Feed
Connect to INDstocks WebSocket on market open (09:25 AM)
Subscribe to tick-level data for both instruments
Aggregate ticks into 1-min candles in memory using OHLCV accumulator
Emit 'candle_closed' event at each minute boundary to trigger indicator computation
Auto-reconnect with exponential backoff on disconnect
Heartbeat check every 30 seconds; log feed health to monitoring

3.2 Module 2 — Technical Indicator Engine
All indicators computed server-side in Python using pandas-ta or TA-Lib. Indicator values are computed fresh on every candle_closed event. Results stored in indicator cache (Redis) keyed by instrument + timeframe + candle_timestamp.

Core Indicator Stack (Minimum Required)


Confluence Scoring
Each indicator produces a directional vote: +1 (bullish), -1 (bearish), 0 (neutral)
Weighted confluence score computed: ∑(indicator_vote × weight) / ∑weights
Score > +0.6 triggers BUY consideration; Score < -0.6 triggers SELL consideration
Score between ±0.6 results in HOLD — no signal fired
Weights configurable per instrument; default weights stored in config YAML

3.3 Module 3 — AI Signal Engine (Claude Integration)
When confluence score crosses threshold, the system constructs a structured prompt payload and sends it to Claude API for final signal reasoning and narrative generation.

3.3.1 Prompt Payload Structure
Instrument name, current candle OHLCV (5m and 15m)
All indicator values with their directional state (e.g., RSI=68 OVERBOUGHT, MACD=BULLISH CROSSOVER)
Higher timeframe context: 1hr trend direction, daily trend, proximity to key S/R
Recent 20-candle OHLCV summary (open, high, low, close as compact array)
Pre-computed confluence score and individual indicator votes
Market context: time of day, session phase (morning/midday/expiry), day of week

3.3.2 Claude Output Schema (JSON)
signal: BUY | SELL | HOLD
confidence: 0–100 integer (percent)
entry_zone: { low: price, high: price }
stop_loss: price
target_1: price
target_2: price
risk_reward_ratio: float
reasoning: string (max 3 sentences — why this signal)
warnings: array of strings (e.g., 'Near major resistance', 'Low volume')
invalidation: string (what would invalidate this trade)

3.3.3 AI Engine Rules
Claude must never override a HOLD if confluence score is between ±0.6 — hard rule enforced in prompt
System prompt includes trading persona: veteran NSE intraday trader, risk-first mindset
Temperature set to 0.1 for deterministic, consistent signal logic
Response must be valid JSON only — use structured output parsing with fallback
If Claude API fails, system falls back to rule-based signal (confluence score only) and flags signal as 'AI_UNAVAILABLE'

3.4 Module 4 — Paper Trading Engine
3.4.1 Order Simulation
On BUY signal: simulate long entry at next candle open price (no look-ahead)
On SELL signal: simulate short entry at next candle open price
Track simulated fills: entry price, timestamp, instrument, quantity (₹1L notional per trade)
Auto SL: place simulated stop at Claude-suggested SL level
Auto Target: place simulated target orders at T1 and T2 levels
Exit triggers: SL hit, T1/T2 hit, or EOD square-off at 03:10 PM

3.4.2 Position Management
Maximum 2 open positions simultaneously (one per instrument)
No pyramiding in Phase 1 — one signal per instrument at a time
Trailing stop activation: when T1 hit, trail SL to entry (breakeven)
Force-close all positions at 03:10 PM regardless of P&L

3.5 Module 5 — Analytics & Reporting Dashboard
Real-Time Dashboard Panels
Live Signal Feed: rolling list of BUY/SELL/HOLD signals with timestamp, instrument, confidence
Open Positions: current paper positions with live unrealized P&L
Trade Log: full history of all trades with entry/exit/SL/targets
P&L Chart: cumulative paper account equity curve
Accuracy Metrics: win rate, average R:R, profit factor, max drawdown, Sharpe ratio
Indicator Dashboard: live values for all indicators for both instruments across timeframes

Daily/Weekly Reports
EOD summary email/log: trades taken, P&L, accuracy, notable signals missed
Weekly accuracy report comparing signal confidence vs actual outcome
Signal quality heatmap: time-of-day performance analysis

5. System Architecture Design
ChartEdge AI follows an event-driven microservices architecture. Each module is a standalone service communicating via an internal message broker (Redis Pub/Sub or BullMQ). This allows individual services to be scaled, replaced, or upgraded independently.

5.1 High-Level Architecture Overview
  [INDstocks WebSocket / REST API]
↓  tick stream / historical OHLCV
  DATA INGESTION SERVICE  (Node.js / Python)
↓  candle_closed events → Redis Pub/Sub
  INDICATOR ENGINE  (Python + pandas-ta)
↓  indicator_snapshot + confluence_score → Redis
  AI SIGNAL ENGINE  (Python + Claude API)
↓  signal_event (JSON) → Redis + PostgreSQL
  PAPER TRADE ENGINE  (Python)
↓  trade_update → WebSocket → Frontend
  DASHBOARD (Next.js + TradingView Lightweight Charts)

5.2 Service Breakdown


5.3 Data Flow — Intraday Signal Generation
09:25 AM: data-ingestion connects WebSocket, subscribes to Nifty50 + BankNifty ticks
Each tick: accumulate into 1-min OHLCV candle in memory
On minute boundary: finalize candle, write to TimescaleDB, publish candle_closed:{instrument}:{timeframe} to Redis
indicator-engine receives candle_closed, loads last N candles from DB, computes all indicators, writes snapshot to Redis, publishes indicator_ready event with confluence score
ai-signal-engine: if |confluence_score| >= 0.6, build prompt payload from Redis snapshot, call Claude API
Claude returns JSON signal; ai-signal-engine validates schema, writes to PostgreSQL signals table, publishes signal_event to Redis
paper-trade-engine receives signal_event, simulates fill at next candle open, updates positions table
analytics-service detects new signal via DB trigger or Redis subscription; pushes update to frontend via WebSocket
Frontend dashboard updates signal feed, positions panel, P&L chart in real-time

5.4 Database Schema
TimescaleDB — candles (hypertable)
  candles(time TIMESTAMPTZ, instrument TEXT, timeframe TEXT, open FLOAT, high FLOAT, low FLOAT, close FLOAT, volume BIGINT)
PostgreSQL — signals
  signals(id UUID, created_at TIMESTAMPTZ, instrument TEXT, signal TEXT, confidence INT, entry_low FLOAT, entry_high FLOAT, stop_loss FLOAT, target_1 FLOAT, target_2 FLOAT, rrr FLOAT, reasoning TEXT, warnings JSONB, indicator_snapshot JSONB, confluence_score FLOAT, ai_model TEXT)
PostgreSQL — paper_trades
  paper_trades(id UUID, signal_id UUID FK, instrument TEXT, direction TEXT, entry_price FLOAT, entry_time TIMESTAMPTZ, exit_price FLOAT, exit_time TIMESTAMPTZ, exit_reason TEXT, pnl FLOAT, status TEXT, sl_price FLOAT, t1_price FLOAT, t2_price FLOAT)

7. Risk Management & Compliance
7.1 System Risk Controls
Kill switch: single API endpoint to halt all signal generation and close all paper positions immediately
Max drawdown circuit breaker: if paper account drops > 5% in a single day, system pauses signals until next market day
Signal rate limiter: maximum 3 signals per instrument per hour to prevent overtrading
Confidence floor: signals below 60% confidence are logged but not executed in paper engine
Duplicate signal prevention: if position already open for an instrument, new signals are queued not executed

7.2 Data Quality Controls
Stale data detection: if no tick received for > 60s during market hours, flag as FEED_STALE and suppress signals
Price sanity check: reject candles where OHLCV values deviate > 5% from last close (circuit filter proxy)
Indicator validity check: NaN indicator values result in automatic HOLD, never a directional signal

7.3 Phase 2 Live Trading Risk (Future)
Maximum position size per trade: ₹1,00,000 notional
Maximum daily loss limit: ₹5,000 — hard stop, no override
Manual review required before enabling live trading after paper phase
Regulatory: Ensure compliance with SEBI algo trading guidelines before live deployment

9. AI Prompt Engineering Specification
9.1 System Prompt
The following system prompt should be used for all Claude signal generation calls:
  You are a veteran NSE intraday technical trader with 15+ years experience trading Nifty 50 and Bank Nifty. You built consistent profits using pure technical chart analysis. You are risk-first: protecting capital is more important than catching every move. You analyse multi-timeframe confluence and never trade on a single indicator.

  Rules you ALWAYS follow:
  1. Never give a directional signal if confluence_score is between -0.60 and +0.60. Output HOLD.
  2. Always size SL based on ATR, not arbitrary points.
  3. Minimum R:R must be 1.5:1 to recommend entry.
  4. Respond ONLY with valid JSON matching the exact schema provided. No preamble, no markdown.
